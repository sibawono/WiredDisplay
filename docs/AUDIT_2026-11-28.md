## Performance

### PERF-01 (HIGH): Ultra cannot hold 60 Hz in motion, and its latency doubles

- **Where:** `macOSHost/Host/VideoEncoder.swift:717-723`, the per-frame `VTCompressionSessionCompleteFrames` on the 4:4:4 lane added in P1-091, called inside `encodePrepared` on `encodeQueue` with `submitLock` held.
- **Why it matters:** the owner runs Ultra (4:4:4 10-bit, 2732 × 2048). The flush is synchronous, so the next frame is not submitted until the previous one has left the encoder. Throughput becomes 1 / encode time. When encode time passes 16.7 ms, frames are replaced before encode and the iPad gets 25-35 fps.
- **Evidence (host log, 28 Nov, 4:4:4/10 lane only):**

  | Hour | Encode p50 (lane mean) | Captured fps | Encoded fps | Capture to send queue p50 / p95 / p99 |
  |---|---|---|---|---|
  | 12:00 | 7.5-19 ms | 52.1 | 52.2 | 10.3 / 17.8 / 76.3 ms |
  | 13:00 | 11-24 ms | 44.1 | 44.1 | 10.4 / 55.5 / 101.1 ms |
  | 14:00 | 21-24 ms | 33.3 | 29.9 | 27.4 / 42.8 / 50.9 ms |
  | 15:00 | 20-30 ms | 27.5 | 25.3 | 34.9 / 46.3 / 53.9 ms |
  | 16:00 | 19-25 ms | 34.1 | 32.1 | 27.0 / 43.4 / 48.9 ms |

  A typical 16:38 window: `4:4:4/10 138 frames, encode p50 25.0 p95 26.2 ms ... replaced before encode 50` (36 % of frames thrown away), `video encoded: 17.2 fps`.
  On the iPad at 16:40-16:42: `enqueued->glass p50 31-35 ms`. End to end in motion is therefore about 27 + 1 + 33 ≈ 60 ms, against the ~9.5 ms host figure published for 0.5.5, which holds only for small updates (13:17: 1 KB frames, encode p50 7.4 ms).
- **Cause, as far as the logs show:** encode time on the 4:4:4 lane rises with frame content (a 1 KB frame 7 ms; 10-190 KB frames 20-30 ms). The synchronous flush removes all pipelining, so a slow frame also blocks the next one. Not proven: no A/B was run, because the brief forbids code changes before approval.
- **Proposed fix (in order, each measured A/B on the owner's desktop with the same motion):**
  1. Flush only at the end of a burst: call `CompleteFrames` from `drainEncodes` when `pendingEncode` is empty after an encode, not after every frame. During motion the next frame pushes the previous one out anyway; the last frame of a burst still goes out immediately, so the P1-091 typing fix stays.
  2. Set `kVTCompressionPropertyKey_PrioritizeEncodingSpeedOverQuality = true` on the 4:4:4 lane only, and compare encode p50 and picture (text edges) at the same bitrate.
  3. If Ultra still cannot hold 60 fps: an adaptive Ultra that moves heavy motion to the 4:2:0 lane when the 4:4:4 encode p95 passes 16 ms for 1 s, and returns once still (the Balanced machinery already exists).
- **Risk:** medium. Step 1 can bring back a held frame if the drain logic is wrong; the 4:4:4 test from P1-091 (typing at low fps) must be repeated. Step 2 may soften text slightly.

### PERF-02 (MEDIUM, carried over from IMP-05): iPad presentation takes two refreshes

- **Where:** `iPadOSClient/WiredDisplayClient/Sources/MetalVideoRenderer.swift` (present path).
- **Evidence:** iPad log 16:40-16:42: `decode 4.0-6.1 ms, GPU 1.3 ms, submit->glass p50 19-29 ms, p95 ~32 ms`. Decode and GPU are small; composition and scan-out are 2 of every 3 ms the iPad spends.
- **Proposed fix:** the IMP-05 experiment, now with a clear target: one refresh less (~16 ms). Try `presentsWithTransaction = false` with present at a deadline from `CADisplayLink.targetTimestamp`, and test with the local cursor layer hidden to see whether it blocks direct composition.
- **Risk:** medium-high, uncertain gain (D-042 tried `CAMetalDisplayLink` without a gain). Experiment only.

### PERF-03 (LOW): a rejected encoder property on the Balanced lane

- **Where:** `VideoEncoder.swift:267-269`. The comment says only the 4:4:4 lane rejects `MaxFrameDelayCount`, but the warning `encoder property MaxFrameDelayCount not applied: -12900` appears 18 times, each right before `4:2:0 conversion on the GPU` in hybrid (Balanced) sessions.
- **Why it matters:** if the low-latency 4:2:0 lane does not take the property, the code cannot assume zero held frames there.
- **Proposed fix:** confirm per lane which property is rejected (log the lane label), then either drop the property for that lane or apply the P1-091 end-of-burst flush to it too. **Risk:** low.

## Bugs and security

### BUG-01 (HIGH): a version mismatch turns into a reconnect loop

- **Where:** `Shared/Session/Messages.swift:421` throws `unknownTag`; `macOSHost/Host/HostController.swift:1910` and `iPadOSClient/WiredDisplayClient/Sources/ClientSession.swift:542, 568` close the session on it.
- **Evidence:** 28 Nov 13:17:12-13:17:39, six sessions in 27 s each ended `protocol error: unknownTag(22)` (tag 22 = `biometricPublicKey`, sent by a newer iPad build to an older host). Every cycle created and released a virtual display, started and stopped the speaker bridge, and moved the Mac's default output to "iPad Speaker" and back.
- **Why it matters:** the Mac app (DMG) and the iPad app (IPA or SideStore) update separately. Any new control message makes every older peer drop the session, so users see a flickering display and audio switching until both sides are updated.
- **Proposed fix:** decode an unknown *control* tag as an ignorable message (log once per session), keep unknown video/input/audio data fatal, and add a vector to `Tests/Vectors` so the Android client follows the same rule. Optionally send the peer's version in the hello and show "Update the iPad app" in the panel. **Risk:** low.

### SEC-01 (MEDIUM): the iPad is reachable and pairable over Wi-Fi on every network

- **Where:** `ClientSession.swift:330-370` (Wi-Fi listener on 9101 and Bonjour `_wireddisplay._tcp`, started with the app), `ClientSession.swift:552-560` (an unknown Mac gets a pairing prompt whatever the transport).
- **Why it matters:**
  - The listener runs even when the Mac is set to USB-C only. On a café or office network the iPad advertises its device name (often the owner's name) and a key fingerprint prefix.
  - Any machine on that network can connect and raise "Pair with “<any name>”?". If the user taps Pair, that machine receives the iPad's touch, keyboard (including whatever is typed on the Magic Keyboard) and, if on, the microphone.
  - The host already refuses TOFU on Wi-Fi (P1-079); the iPad side does not.
- **Proposed fix:** accept first-time pairing over USB-C only (Wi-Fi only for already paired Macs); advertise only after a paired Mac has enabled Auto or Wi-Fi over USB-C, or behind an iPad switch; use a generic service name. **Risk:** low-medium (Wi-Fi-first users must pair over the cable once; the guide must say so).

### SEC-02 (MEDIUM): any process of the user can raise a Touch ID / Face ID sheet

- **Where:** `macOSHost/Host/PamBridgeServer.swift:215-221` accepts a peer with `euid == 0 || euid == getuid()`; the `reason` string comes from the client (`:228`) and is forwarded to the iPad (`HostFleet.swift:60-80`).
- **Why it matters:** a script or app running as the user can open the socket and send `service = "lockscreen"` or `"admin"` with any reason text. The iPad then pops its biometric sheet at once (P1-089). The signature is useless to the attacker, because the real PAM module and AuthPlugin use their own fresh nonce. The risk is spoofed prompts that train the owner to approve without reading.
- **Proposed fix:** accept only `euid == 0`: `sudo`'s PAM stack and the privileged AuthPlugin mechanisms both run as root. Show text on the iPad built from the service name (`sudo`, Lock Screen, Admin), not the free `reason`. **Risk:** low; test `sudo`, Lock Screen and one admin dialog afterwards.

### SEC-03 (LOW-MEDIUM): a remote or background `sudo` looks like a local one

- **Where:** `MacVirtualDevices/PamModule/pam_wireddisplay.c:259-264`.
- **Why it matters:** the iPad shows "Approve sudo for <user> on Mac" for a `sudo` typed at the Mac, run over SSH, or started by a background script. The owner approves the wrong thing more easily.
- **Proposed fix:** read `PAM_RHOST` and `PAM_TTY`; return `PAM_IGNORE` when `PAM_RHOST` is set (password as usual), and put the TTY into the request so the iPad can say "sudo in Terminal (ttys003)". **Risk:** low. Needs a module rebuild and the owner's reinstall through Install Extras.

### SEC-04 (LOW): AuthPlugin admin mechanism details

- **Where:** `MacVirtualDevices/AuthPlugin/WiredDisplayAuth.c`, `resolve_console_user` and `unlock_worker`.
- **Why it matters:**
  - For `admin`, the username is taken from the authorization context first. A requesting app can pre-fill that hint. Impact is limited to Macs with more than one enrolled admin, but the right answer is the console user only.
  - `unlock_worker` checks `deactivating`, then verifies and calls `SetResult` with no atomic hand-off. A deactivation in between (password typed at the same moment) calls `SetResult` on a deactivated mechanism.
- **Proposed fix:** in admin mode require hint == console user; replace the check with `atomic_exchange` on a "result sent" flag before `SetResult`. **Risk:** low; needs a rebuild and reinstall.

Checked in the Touch ID path and found sound: the nonce comes from `SecRandomCopyBytes` in root code; the signed message has a domain tag plus service and user; the key file must be root-owned, a regular file, not group/world-writable, read with `O_NOFOLLOW`; both ends check the peer UID; every failure returns `PAM_IGNORE`, so the password always works.

### BUG-02 (MEDIUM): the enrolment instructions are stale since 0.5.6

- **Where:** `macOSHost/Host/main.swift:348-352` copies `sudo scripts/install-pam.sh` (a path that only exists in a source checkout); `StatusPanel.swift:487-491` ("Copy Setup Command", "run the copied sudo command in Terminal"); `ClientUI.swift:1158` ("Run install-pam.sh on your Mac"); `main.swift:271` reports "installed" from the `.so` alone.
- **Why it matters:** a DMG user who follows the panel gets `No such file or directory`. The panel also says "installed" when the Lock Screen plugin or the user's key file is missing.
- **Proposed fix:** point both screens to "Install Extras" in the DMG; derive the status from the `.so`, `WiredDisplayAuth.bundle` and the user's `pam_keys/<user>.pub`; show which part is missing. **Risk:** none (copy and status only).

### BUG-03 (LOW): duplicate unbound controller race

- **Where:** `macOSHost/Host/HostFleet.swift:150-153` (watcher thread), `:239-243` (`setTransportMode`, main) and `:288-293` (`setAndroidAoaApproved`, main): each checks `controllers` and then calls `add` outside the lock.
- **Why it matters:** switching Connection to Auto or Wi-Fi while the watcher runs can create two unbound controllers that both dial the same Bonjour service.
- **Proposed fix:** do the check and the append in one `lock.withLock`. **Risk:** low.

### BUG-04 (LOW): the top third of "Mac speaker level" probably does nothing

- **Where:** `HostAudioBridge.swift:45, 118, 138, 160`; `HostController.swift:642` allows 1.5.
- **Evidence:** the owner's setting is 150 % (`Mac speaker mirror started ... level 150%`). The value goes to `AVAudioMixerNode.outputVolume`, which Apple documents as 0.0-1.0.
- **Proposed fix:** measure first (a tone at 100 % and 150 %). If it is clamped: either cap the slider at 100 %, or apply real gain with `AVAudioUnitEQ.globalGain` plus a limiter. **Risk:** low.

### LOG-01 (MEDIUM): the log loses the evidence it is meant to keep

- **Where:** `VideoEncoder.swift:701` samples with `sent % 300 == 0` on a nanosecond clock. On Apple Silicon the clock moves in 41.67 ns steps, so the test passes on 1 frame in 36, not 1 in 300 (the comment says "every 5 s").
- **Evidence:** 15,361 of 30,041 lines (51 %) in the current log are `frame host` samples; with the 5 MB rotation the two files cover about 19 hours, and one file about 4.5 hours. On the iPad, `speaker packets received` is written every 2.5 s.
- **Proposed fix:** a frame counter (every 300th frame) or one summary per 5 s with p50/p95; the same for the speaker packet lines on both sides. **Risk:** none.

## How each fix must be proven (owner: "setiap fixing menghasilkan clean status ... bukan membuat bug, kerusakan atau penurunan performa")

A fix ships only when every line below holds; otherwise it is reverted, not tuned in place.

1. **One fix per change**, with its own CHANGELOG entry, so any regression points to one diff and reverts alone.
2. **Clean build and tests**: `swift build --product WiredDisplayHost` with no new warnings, `swift test` green (199 today, plus the new test for the fix), the iPad Release build succeeds.
3. **A test that fails before the fix** wherever the logic can be unit-tested (BUG-01 unknown tag, BUG-03 race, SEC-02 peer check, LOG-01 sampler, the PERF-01 drain decision).
4. **A/B on hardware for anything on the video or audio path**, same desktop, same motion, same preset, at least 2 minutes per variant, numbers from the logs:

   | Fix | Must improve | Must not get worse (tolerance) |
   |---|---|---|
   | PERF-01 | Ultra encoded fps in motion, capture to send queue p50/p95 | Typing latency at low fps (the P1-091 case), encode p99, iPad enqueued to glass, text sharpness at the same bitrate |
   | PERF-02 | iPad submit to glass p50 | Presented fps, dropped/replaced frames, cursor overlay |
   | PERF-03 | No held frame on the Balanced lane | Balanced capture to send queue p50 (±0.5 ms) |
   | BUG-04 | Measured level at 150 % vs 100 % | No clipping, no change at ≤ 100 % |
   | LOG-01 | Log lines per hour | Same p50/p95 values reported |

5. **Touch ID changes (SEC-02 to SEC-04)**: `sudo`, the Lock Screen and one admin dialog each tested with the iPad approving, the iPad cancelling, and the iPad disconnected (password must still work). The modules are rebuilt and installed only by the owner through Install Extras.
6. **Physical checks before release**: USB-C session up, reconnect after unplug, 3 display-sleep cycles, lock and unlock, audio on both speakers; the log shows no new warning type.
7. **Report per fix**: what was measured, before and after, and what was NOT run.

Suggested order: BUG-01, BUG-02, LOG-01 (low risk, immediate stability and evidence), then SEC-01 and SEC-02, then PERF-01 with A/B, then the rest.
